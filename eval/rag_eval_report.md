# RAG 落地评测对比报告

- 日期：2026-10-20
- 项目：ticket-agent（电商售后工单 Agent）
- 改动：将 `agent/tools.py` 的 `_search_policy` 从「本地 mock 关键词匹配」替换为
  「基于硅基流动 bge-m3 的语义检索（`agent/rag.py` + 15 条 / 4669 字真实语料 `data/policies.md`）」，
  并在 `agent/prompts.py` 增加「政策咨询必须检索、无订单号也得查」的约束。
- 评测脚本：`eval/run_eval.py`（L1 确定性断言 + 发布门禁）

## 一句话结论

RAG 接入后，行为正确性零回归（24/24 全绿，门禁通过），代价是单次评测总成本
从 0.0600 元升至 0.1618 元（约 2.7 倍），P95 延迟从 3083ms 升至 4018ms。
符合「先保证不 regression，再谈增强」的生产级改动原则。

## 发布门禁结果

- 对抗用例（adversarial）失败数 = 0 → 满足「对抗零容忍」
- L1 通过率 = 100% ≥ 95% → 满足门槛
- **结论：通过门禁，可发布**

## 成本/延迟上升的原因（面试可讲）

1. 政策类问题从「1 步自答」变为「2 步（先检索 → 再基于原文答）」。
   多出的那一步 = 多一次 LLM 调用，且把检索到的政策原文注入上下文，
   使输入 token 增加；LLM 按 token 计费，故成本上升。
2. 每次政策查询多一次 embedding 网络往返（硅基流动 bge-m3，免费额度内不花钱，但增加延迟）。

即：**RAG 用「更多 token + 稍慢」换取「答案更准确、不凭记忆编造」**。
